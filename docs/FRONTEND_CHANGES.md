# Изменения во frontend

## Кратко

Frontend был подготовлен к серверному запуску и частично связан с backend. Теперь проект можно запускать в Docker вместе с backend, PostgreSQL и Nginx, а frontend может обращаться к backend через единый путь `/api`.

## Что добавлено

### 1. Docker-сборка frontend

Добавлены файлы:

- `Dockerfile`
- `.dockerignore`

Теперь frontend можно собирать и запускать как Docker-контейнер.

Контейнер запускает приложение на внутреннем порту:

```text
3000
```

Снаружи frontend открывается через Nginx:

```text
http://IP_СЕРВЕРА
```

---

### 2. Настройка адреса backend через переменные окружения

Добавлена поддержка переменной:

```env
NEXT_PUBLIC_API_URL=/api
```

Это значит, что frontend обращается к backend не напрямую по `:8080`, а через Nginx:

```text
/api → backend:8080
```

Плюс такого подхода: IP сервера не нужно прописывать в коде frontend.

---

### 3. Добавлен API-helper для связи с backend

Добавлен файл:

```text
lib/backend-api.ts
```

В нём реализованы функции для обращения frontend к backend:

- login;
- register;
- получение текущего пользователя;
- получение стартовых данных через bootstrap;
- хранение backend JWT-токена;
- очистка токена при logout.

---

### 4. Frontend начал использовать backend-авторизацию

Раньше регистрация и вход работали только локально на frontend через `localStorage`.

Теперь при входе/регистрации frontend сначала пытается обратиться к backend:

```text
POST /api/auth/login
POST /api/auth/register
GET /api/users/me
```

Если backend доступен, пользователь авторизуется через сервер, получает JWT-токен и данные профиля.

---

### 5. Добавлен fallback на локальный режим

Если backend временно недоступен, frontend не падает полностью, а пробует использовать старую локальную логику через `localStorage`.

Это сделано для совместимости с уже существующим frontend-прототипом.

---

### 6. Добавлена первичная загрузка данных с backend

При старте приложения frontend вызывает:

```text
GET /api/public/bootstrap
```

Этот endpoint отдаёт стартовые/demo-данные с backend.

Frontend записывает эти данные в свои локальные хранилища, чтобы существующие экраны могли продолжить работать без полного переписывания всей логики.

---

### 7. Обновлена форма регистрации/входа

Файл:

```text
components/register-form.tsx
```

Изменения:

- `onLogin` и `onRegister` теперь могут быть асинхронными;
- форма ожидает ответ backend;
- ошибки backend корректно обрабатываются;
- сохранён старый локальный fallback.

---

### 8. Обновлена главная логика приложения

Файл:

```text
app/page.tsx
```

Изменения:

- добавлен вызов backend bootstrap при старте;
- добавлена серверная регистрация;
- добавлен серверный login;
- добавлена очистка backend-токена при logout;
- добавлена общая логика перехода пользователя после авторизации;
- сохранена совместимость со старым localStorage-режимом.

---

### 9. Добавлена заготовка GitHub Actions

Добавлен workflow:

```text
.github/workflows/deploy.yml
```

Он рассчитан на будущий deploy через GitHub push.

При push в ветку `main` workflow сможет подключиться к серверу по SSH и запустить deploy-скрипт.

Для работы нужны GitHub Secrets:

```text
SERVER_HOST
SERVER_USER
SERVER_SSH_KEY
```

---

### 10. Обновлён README

В `README.md` добавлены заметки по серверному запуску:

- Docker;
- backend API;
- bootstrap;
- переменные окружения;
- запуск через Nginx `/api`.

## Как теперь работает frontend

Схема работы:

```text
Пользователь открывает сайт
        ↓
Nginx отдаёт frontend
        ↓
Frontend делает запросы на /api
        ↓
Nginx проксирует /api в backend
        ↓
Backend работает с PostgreSQL
```

## Что уже связано с backend

Сейчас frontend связан с backend в следующих местах:

- регистрация;
- вход;
- получение текущего пользователя;
- получение стартовых данных через bootstrap;
- хранение JWT-токена;
- logout с очисткой токена.

## Что пока осталось локальным

Не все действия frontend полностью переведены на backend API.

Часть экранов всё ещё может использовать локальные хранилища браузера:

```text
localStorage
```

Это значит, что отдельные действия в интерфейсе могут пока сохраняться только локально в браузере, а не в PostgreSQL.

## Что нужно доработать следующим этапом

Чтобы frontend стал полностью production-ready, нужно постепенно заменить локальные действия на API-запросы:

- HR-воронка;
- изменение статусов кандидатов;
- заметки HR;
- приглашения;
- архив;
- достижения студента;
- мероприятия организатора;
- уведомления;
- настройки профиля.

Целевая логика должна быть такой:

```text
Действие пользователя → API-запрос → backend → PostgreSQL → обновление UI
```

## Итог

Frontend переведён из состояния автономного локального прототипа в состояние серверного MVP:

- его можно запускать в Docker;
- он работает через Nginx;
- он может обращаться к backend через `/api`;
- он поддерживает серверную авторизацию;
- он получает стартовые данные с backend;
- он готов к дальнейшему поэтапному переводу всех экранов на полноценные backend API.
